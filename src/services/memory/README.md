# 🧠 Memory Service — Довгострокова Пам'ять

> **Роль:** "Hippocampus" (Гіпокамп)
> **Відповідальність:** Зберігання фактів, уподобань та профілю користувача, які мають жити довше, ніж одна сесія.

Це не проста історія чату ("хто що сказав"). Це **семантична пам'ять** ("що ми дізналися про користувача").

---

## 🏗️ Структура

```
src/services/memory/
├── __init__.py         # Експорти (MemoryService + Models)
├── models.py           # 📦 SSOT для Memory Models (Fact, UserProfile, etc.)
├── base.py             # Базовий клас з DB хелперами
├── facts.py            # CRUD для фактів (Gating logic)
├── profiles.py         # CRUD для профілів користувачів
├── context.py          # Формування контексту для промптів
├── summaries.py        # Робота з саммарі
├── maintenance.py      # TTL, cleanup expired facts
└── tasks.py            # Background Celery tasks
```

> ℹ️ **SSOT:** `models.py` — канонічне місце для `Fact`, `UserProfile`, `MemoryContext` etc.
> Старий шлях `src/agents/pydantic/memory_models.py` залишений як deprecated shim.

## 🏗️ Архітектура (No Conflict)


Цей сервіс працює паралельно з `SessionStore`, не заважаючи йому.

| Компонент | Таблиця БД | Хранить | Термін життя |
| :--- | :--- | :--- | :--- |
| **SessionStore** (`src/services/storage`) | `agent_sessions` | Поточний стан FSM, діалог, змінні. | Хвилини/Години (до закриття продажу). |
| **MemoryService** (`src/services/memory`) | `mirt_memories` | Факти ("клієнт любить червоне"), профайл. | **Назавжди** (Long Term). |

## 🔗 Де використовується? (Usage Map)

Я провів повний аудит коду. Цей сервіс інтегрований у всі ключові вузли системи:

| Файл | Роль використання | Опис |
| :--- | :--- | :--- |
| **`src/agents/langgraph/nodes/memory.py`** | **CORE LOGIC** | Основний споживач. Агент викликає пам'ять, щоб знайти факти перед генерацією відповіді (RAG). |
| **`src/agents/pydantic/deps.py`** | **Dependency Injection** | Створює екземпляр `MemoryService` і передає його агентам (`deps.memory`). |
| **`src/server/main.py`** | **Lifecycle** | Ініціалізується при старті сервера (перевірка підключення до БД). |
| **`src/services/summarization/summarization.py`** | **Helper** | Використовує пам'ять для збереження саммарі діалогів. |
| **`src/workers/tasks/memory.py`** | **Maintenance** | Фонова задача (Celery), яка видаляє прострочені факти (`cleanup_expired`). |
| **`src/server/routers/health.py`** | **Diagnostics** | Health check ендпоінт перевіряє, чи жива пам'ять. |

## 🛠️ Як це працює?

### 1. Gating (Фільтр важливості)
Ми не запам'ятовуємо все підряд ("користувач сказав 'привіт'").
Модуль використовує механізм **Gating** в `facts.py`:
*   `importance`: Наскільки цей факт важливий? (Поріг: `0.6`)
*   `surprise`: Нвскільки це нова інформація? (Поріг: `0.4`)

Тільки якщо факт долає ці пороги, він записується в БД.

### 2. Semantic Search
Факти зберігаються разом з **векторними ембеддінгами** (`embedding`).
Це дозволяє знаходити релевантні спогади за змістом, а не за ключовими словами.
*Приклад:* Якщо юзер питає "Є щось для мене?", ми шукаємо факти про його стиль і розмір.

## 🛡️ Надійність (Ironclad)

*   **Lazy Models:** Моделі імпортуються всередині методів, щоб уникнути циклічних залежностей з `src/agents`.
*   **Safe DB:** Використовує окремі підключення `psycopg` і транзакції.
*   **Fallback:** Якщо Postgres недоступний, сервіс просто вимикається (`self._enabled = False`), не крашачи бота.

## 📝 Вердикт
Це фундамент **інтелекту** бота.
Без нього бот буде "рибка Дорі" — пам'ятатиме тільки поточну розмову.
**Конфліктів немає.** Використовується скрізь, де потрібно знати контекст клієнта.
