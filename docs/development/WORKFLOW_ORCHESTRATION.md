# Workflow Orchestration для паралельних задач

## 1) Режим Plan-by-default

Вмикаємо plan mode для будь-якої нетривіальної задачі (3+ кроки, архітектурні рішення, зміни в декількох модулях).

### Обов'язкові артефакти перед реалізацією
- Контекст: що саме змінюємо і чому.
- Межі змін: які файли/модулі дозволено змінювати.
- Ризики: що можна зламати.
- Перевірка: які тести/чек-листи підтвердять коректність.

### Правило зупинки
Якщо з'явилась нова невідомість, флейки тестів або відхилення від плану:
1. STOP.
2. Оновити план.
3. Лише після цього продовжити.

## 2) Стратегія підзадач (subagents mindset)

Для паралельної роботи використовуємо принцип «одна підзадача — один трек».

### Типи треків
- Research track: дослідження існуючої логіки/контрактів.
- Implementation track: точкові зміни коду.
- Verification track: тести, дифи поведінки, smoke checks.

### Як не ламати систему при паралельній роботі
- Кожен трек має власний scope файлів.
- Заборонені «перехресні» зміни без повторного узгодження плану.
- Інтеграція треків тільки через явні контракти (інтерфейси, схеми, тести).

## 3) Self-improvement loop

Після кожного виправлення від користувача:
1. Додаємо новий урок у `tasks/lessons.md`.
2. Формулюємо правило, яке запобігає повторенню помилки.
3. На старті наступної сесії переглядаємо релевантні уроки.

## 4) Verification gate перед завершенням

Задача не може бути "Done", доки немає доказу коректності:
- Пройдені тести або зафіксовані обмеження середовища.
- Перевірений behavior diff (до/після) для критичних змін.
- Самоперевірка: "Чи підписав би це Staff Engineer?"

## 5) Balanced elegance

Для нетривіальних змін перед фіналізацією ставимо питання:
- "Чи є простіше рішення з меншим ризиком?"
- "Чи не є це тимчасовим хаком?"

Для простих змін не переускладнюємо.

## 6) Autonomous bug fixing

При баг-репорті:
- Відтворити проблему.
- Знайти кореневу причину.
- Виправити.
- Довести виправлення тестами/перевірками.

Без зайвого контекст-світчингу від користувача.

## 7) Протокол виконання задачі

1. Створити план у `tasks/todo.md` (чекбокси).
2. Підтвердити межі і критерій готовності.
3. Виконувати кроки, відмічаючи прогрес.
4. Після реалізації додати секцію review у `tasks/todo.md`.
5. За наявності корекцій — оновити `tasks/lessons.md`.

## 8) Definition of Done

Задача "готова", якщо:
- План виконано повністю.
- Перевірки виконані і задокументовані.
- Ризики/обмеження явно зафіксовані.
- Наступний інженер може продовжити роботу без прихованого контексту.

## 9) Порядок аварійної починки (anti-conflict protocol)

Для задач типу "проект ламається / є дублювання" порядок фіксований:
1. Спочатку SSOT правил (усунути конфлікт джерел істини).
2. Потім мінімізація стану (checkpointer payload hygiene).
3. Потім CI quality gates (щоб проблема не повернулась).

### Заборонено
- Змінювати одночасно state-machine логіку і роутинг без контрактних тестів.
- Мержити зміни checkpointer без перевірки payload size budget.
- Робити "швидкі" патчі без Task Card і Verification plan.
