# 🏗️ Архітектура PydanticAI + LangGraph (Hybrid Approach): Deep Dive V2

> **Для кого цей документ:** Для Senior/Lead інженерів та CTO, які хочуть знати правду, а не маркетингові слогани.
> **Статус:** Production-Grade Architecture

Цей документ — "рентгенівський знімок" нашої системи. Тут описано не тільки як вона працює, але і **чому вона завдає болю** розробникам (і чому ми цей біль терпимо).

---

## 🧩 1. Фундаментальна Філософія: "Контр-Інтуїтивна Жорсткість"

У світі AI всі женуться за "автономними агентами", які самі придумують собі план.
Ми пішли протилежним шляхом: **Тоталітарний контроль над станом.**

### Архітектурний Сендвіч:

1.  **Top Level: LangGraph (Оркестратор-Наглядач)** 👮‍♂️
    *   **Роль:** Це FSM (Finite State Machine). Він нічого не знає про "зміст" розмови.
    *   **Відповідальність:** Його єдина задача — сказати: *"Ти в стані `OFFER`, твій наступний крок ТІЛЬКИ `PAYMENT` або `SIZE`. Ніяких стрибків."*
    *   **Чому це важливо:** LLM галюцинують. Вони можуть "забути", що клієнт ще не вибрав розмір, і почати просити гроші. Граф фізично забороняє такий перехід.

2.  **Middle Level: PydanticAI (Вузькоспеціалізований Робітник)** 👷
    *   **Роль:** Це логіка всередині конкретного вузла (Node).
    *   **Відповідальність:** Отримати брудний текст -> Повернути чисту Pydantic модель.
    *   **Механіка:** Ми використовуємо `Structured Output`. Ми не просимо LLM "відповісти JSON-ом". Ми змушуємо її генерувати аргументи для функції-валідатора.

3.  **Bottom Level: Core Domain (Бізнес-Логіка)** 💼
    *   **Роль:** Чистий Python код (сервіси, репозиторії).
    *   **Відповідальність:** Зберегти в БД, порахувати суму, відправити в CRM. Тут немає AI.

## 💡 2. Чому саме так? (Rationale Expansion)

### А. "Захист від дурня" (LLM Foolproof)
У звичайному LangChain агенті ("ReAct") модель сама вирішує, який тул викликати.
*   *Ризик:* Модель може зациклитись ("Think: я маю перевірити ціну... Action: check_price... Think: я маю перевірити ціну...").
*   *Наше рішення:* В LangGraph ми жорстко прописуємо ребра (Edges). Модель не "вирішує" куди йти глобально. Вона вирішує тільки локально в межах вузла.

### Б. Тестованість (Testability)
Як протестувати "балакучого" агента? Майже ніяк.
Як протестувати наш вузол?
*   Input: `Deps(state=OFFER)`
*   Mock LLM Output: `Action(add_to_cart)`
*   Assert Output: `NewState == PAYMENT`
Ми можемо писати юніт-тести на кожен вузол окремо, ігноруючи решту графа.

## 💀 3. Слабкі Сторони (The Ugly Truth)

Давайте чесно про те, де ця архітектура "п'є кров".

### 1. "Пекло Бойлерплейту" (Boilerplate Hell) 📝
Щоб додати одну просту фічу (наприклад, "Кнопка 'Передзвоніть мені'"), вам треба:
1.  Оновити `StateSchema` (додати поле `call_requested`).
2.  Оновити `Pydantic Model` відповіді агента (додати поле `call_requested`).
3.  Оновити `Transition Logic` у `transition_reducer.py` (обробка цього поля).
4.  Оновити `Node Logic` (щоб викликати тул).
5.  Оновити `Prompts` (щоб модель знала про цю можливість).
**Ціна:** +5 файлів змін для однієї кнопки.
**Наслідок:** Розробка йде повільніше, ніж на "сирому" OpenAI API.

### 2. "Когнітивне Навантаження" (Cognitive Load) 🤯
Новому розробнику треба тримати в голові три шари абстракції:
*   *"Це `State` графа чи `Deps` агента?"* (Вони схожі, але різні).
*   *"Хто керує переходом: Граф через ребра чи Агент через `Structural Output`?"* (Відповідь: Агент пропонує, Граф затверджує. Це складно усвідомити).
**Наслідок:** Високий поріг входу (Onboarding 1-2 тижні).

### 3. Латентність Серіалізації (Serialization Tax) 🐢
*   LangGraph зберігає стан в Postres/Redis після **кожного** кроку.
*   Це означає `Object -> JSON -> Network -> DB -> Network -> JSON -> Object`.
*   PydanticAI робить те саме для валідації input/output.
**Ціна:** Ми втрачаємо ~100-200мс на чистому "перекладанні байтів" ще до того, як запит піде до LLM. Для Real-time Voice це було б критично. Для чату — терпимо.

### 4. Контекстне Вікно та Гроші (Token Tax) �
LangGraph має тенденцію тягнути за собою *весь* стан (`messages history`).
Якщо ми не будемо обережно "підрізати" історію (trimming), ми будемо відправляти в LLM 100 повідомлень на кожен "чих".
**Ризик:** PydanticAI спрощує роботу з контекстом, але не оптимізує його магічно. Це треба робити руками.

### 5. Debugging Nightmare 🕵️‍♂️
Коли щось ламається, стек-трейс виглядає як "спагетті":
`LangGraph Runner -> Async Loop -> Node Execution -> PydanticAI Agent -> Model Request -> ... -> Crash`.
Зрозуміти *де саме* виникла помилка (у валідаторі Pydantic чи у логіці графа) буває важко без детальних трейсів (LangSmith/Logfire).

## ⚖️ 4. Вердикт: Чи варте воно того?

**ТАК, якщо:**
*   Вам потрібна **передбачуваність**. (Клієнт МАЄ пройти оплату).
*   Бізнес-процес складний і має чіткі етапи.
*   Ви працюєте в команді (типізація рятує від конфліктів).

**НІ, якщо:**
*   Вам треба "швидко MVP за вихідні".
*   У вас простий чат-бот "питання-відповідь" (RAG).
*   Ви один розробник і ненавидите писати класи.

Ми обрали цей шлях, бо будуємо **E-commerce Platform**, а не іграшку. Тут помилка коштує реальних грошей (втрачений клієнт). Тому ми терпимо бойлерплейт заради надійності.
