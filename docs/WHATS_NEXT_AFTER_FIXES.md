# Що робити після виправлення слабких місць

## 1. Перевірити, що все збирається і тести проходять

```powershell
cd c:\Users\Zoroo\Documents\GitHub\Mirt-AI

# Швидкий смоук (граф, імпорти, конфіг)
python -m pytest tests/smoke/ -v --tb=short

# FSM і STATE_5 (критична логіка)
python -m pytest tests/test_fsm_invariants.py tests/scenario/test_state5_scenarios.py -v --tb=short

# Повний набір (довше)
python -m pytest tests/ -v --tb=short
```

Якщо щось падає — виправити перед комітом.

---

## 2. Оновити документацію (якщо змінилася поведінка)

- **docs/AI_LAYER_LOGIC_PROMPTS_BREAKDOWN.md** — якщо змінили роутинг, FSM, підфази STATE_5 або склад промптів, оновити розділи під поточну реалізацію.
- README / DEPLOY.md — якщо з’явилися нові змінні оточення або флаги (наприклад `FSM_STATE5_STRICT_MODE`).

---

## 3. Закомітити зрозуміло

- Один коміт = одна логічна зміна (або один «пачок» пов’язаних виправлень).
- Повідомлення коміту: що саме починено (наприклад: «STATE_5: так/да/ок не завершують діалог до payment proof», «Intent для роутингу тільки з intent_node»).
- Якщо є — посилання на issue або на розбір у docs.

---

## 4. Далі залежно від мети

| Мета | Дія |
|-----|-----|
| Злити в основну гілку | Зробити PR, пройти рев’ю, мерджити після зелених CI. |
| Викати на стейджинг | Після мерджу — деплой за інструкцією з DEPLOY.md. |
| Ще покращити якість | Прогнати eval-датасети: `tests/eval/run_eval.py`, `run_vision_eval.py` (якщо є ключі). |
| Зафіксувати «до/після» | Додати або оновити regression-тести під нову поведінку (наприклад у `tests/regression/` або `tests/scenario/`). |

---

## 5. Короткий чеклист перед мерджем

- [ ] `pytest tests/smoke/` — зелений
- [ ] `pytest tests/test_fsm_invariants.py tests/scenario/test_state5_scenarios.py` — зелений
- [ ] Документація (breakdown / README) відповідає коду
- [ ] Коміти описані зрозуміло
- [ ] Якщо були слабкі місця з розбору — вони або виправлені, або зафіксовані в тестах/доках

Після цього можна робити PR або мерджити в свою гілку і викатувати далі.
